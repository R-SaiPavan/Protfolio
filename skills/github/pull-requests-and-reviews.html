GitHub roadmap / 03

Pull requests and reviews

Use pull requests to explain a change, gather feedback, run checks, and merge with an auditable team decision.

PR workflowReview examplePractice

01 / Review workflow

Make intent and risk visible.

Describe the change

State the problem, the implementation approach, the validation performed, and any rollout or rollback risk.

Keep scope focused

Small, coherent pull requests are easier to review and less likely to mix unrelated decisions.

Use checks

Run automated tests and required checks. Treat failures as evidence to investigate rather than bypass by default.

Merge deliberately

Choose merge, squash, or rebase according to team history conventions and repository policy.

02 / Review example

A useful pull-request summary.

Problem: describe the behavior that needs to change.
Approach: summarize the files and decisions involved.
Validation: list tests, queries, or manual checks run.
Risk: note rollout considerations and recovery plan.
Reviewer focus: correctness, edge cases, data integrity, operational impact, test coverage, and whether the implementation fits the intended scope.

03 / Practice

Interview checks.

What makes a pull request easy to review?

A focused change, clear context, readable commits, relevant tests, and explicit risks or migration steps. Respond to review comments with the reasoning or follow-up change.

What should happen when a required check fails?

Inspect the failure, determine whether it is caused by the change or the environment, fix or document it, and follow repository policy before merging.

How do you handle a disagreement in review?

Clarify the requirement and tradeoffs, refer to conventions or evidence, and reach agreement with the code owner. Record important decisions so future contributors understand them.
