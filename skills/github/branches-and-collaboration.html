GitHub roadmap / 02

Branches and collaboration

Coordinate parallel work, keep changes isolated, and integrate updates while preserving a useful team history.

BranchingWorkflow examplePractice

01 / Collaboration model

Keep work isolated until it is ready.

Feature branches

Use a short-lived branch for a focused change. Regularly synchronize with the base branch to reduce integration surprises.

Merge

Combines histories and preserves branch structure. A merge commit can record when parallel work was integrated.

Rebase

Replays commits onto a new base for a linear history. Avoid rewriting commits already shared unless the team has agreed.

Conflicts

Understand both sides, edit the intended resolution, run tests, stage the resolved files, and finish the merge or rebase.

02 / Workflow example

Sync, resolve, verify, publish.

git switch -c feature/add-validation
git fetch origin
git rebase origin/main
# resolve conflicts and run checks
git push --set-upstream origin feature/add-validation
Example: before opening a pull request, sync with the base branch, resolve conflicts deliberately, run relevant tests, and make the branch available for review.

03 / Practice

Interview checks.

When would you use merge instead of rebase?

Merge preserves branch history and integrates parallel work. Rebase creates a linear sequence by replaying commits. Team conventions and whether commits are already shared should guide the choice.

How do you resolve a conflict safely?

Inspect each conflicted file, understand both intended changes, produce the correct combined result, stage it, run tests, and complete the operation. Do not blindly choose one side.

Why keep branches short-lived?

Smaller change sets reduce drift and make review and integration easier. Frequent synchronization exposes conflicts earlier.
