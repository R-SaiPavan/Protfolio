Optimizer and SQL

Use statistics and EXPLAIN to understand optimizer choices; write SQL that keeps joins, filters, and intermediate data under control.

OptimizerSQL examplesPractice

01 / Query planning

Estimates shape the plan.

Statistics

Statistics provide the optimizer with information about row counts, value distributions, and indexes. They can affect join order, access methods, and redistribution choices.

EXPLAIN

Read planned steps for index access, full scans, joins, redistribution, and spool. Use it before and after a targeted change, then compare to actual runtime.

Spool

Spool holds intermediate query results. Large joins, skew, and weak cardinality estimates can increase spool demand or cause a query to fail.

QUALIFY

QUALIFY filters after analytic/window functions are evaluated, which is useful for top-N and latest-row-per-key patterns.

02 / SQL examples

Collect relevant statistics.

COLLECT STATISTICS COLUMN (customer_id)
ON mart.orders;

Use QUALIFY to select the latest row per customer:

SELECT customer_id, status, updated_at
FROM staging.customer_status
QUALIFY ROW_NUMBER() OVER (
  PARTITION BY customer_id
  ORDER BY updated_at DESC
) = 1;
Practice: explain why you chose the statistic or query pattern, how EXPLAIN changed, and what runtime evidence confirmed the improvement.

03 / Practice

Interview checks.

When should you collect statistics?

Collect them on columns or indexes relevant to filters, joins, and distribution when the optimizer needs better estimates. Refresh them when data changes materially and validate plan impact.

What do you look for in EXPLAIN?

Check access methods, estimated rows, join order, redistribution, full scans, and spool-heavy steps. Compare the plan to query intent and actual runtime evidence.

Why can a query use an index and still be slow?

The access may still return many rows, later joins may redistribute large inputs, estimates may be wrong, or spool and skew may dominate. Examine the full plan rather than one access step.
