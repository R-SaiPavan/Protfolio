01 / Load design

Choose a load path for the data and recovery needs.

Bulk utilities

Teradata environments commonly use utilities such as FastLoad, MultiLoad, or TPT. Selection depends on source, target table state, operation type, concurrency, and platform/version constraints.

Stage and validate

Land source data in a controlled staging area. Validate schema, required keys, counts, and rejected rows before publishing to reporting tables.

Make reruns safe

Assign each load a batch identifier and record status. Design cleanup or restart steps so a retry does not duplicate accepted rows or skip incomplete work.

Monitor operations

Track start/end times, rows loaded, rejects, failures, and downstream readiness. Surface actionable alerts and retain enough context to investigate incidents.

02 / Example flow

Separate load, check, and publish.

-- 1. Load the source batch to a staging table
-- 2. Validate batch_id, keys, and row counts
-- 3. Apply a repeat-safe merge or insert strategy
-- 4. Reconcile target counts and mark the batch complete
Operational example: if a load fails after staging, keep the batch identifier and failure status. Correct or isolate rejected records, then restart from the validated staging step rather than blindly replaying every upstream action.

03 / Practice

Interview checks.

How do you choose between Teradata load utilities?

Start with the required operation, source format, target-table state, and expected volume. Check the utility's restrictions and platform version, then compare operational recovery, throughput, and maintainability.

How do you restart a failed batch safely?

Track batch IDs and step status, preserve or clean staging data intentionally, and make target writes idempotent. Reconcile counts and keys before marking the batch complete.

What metrics belong on a load dashboard?

Track duration, rows read and written, rejects, retry count, freshness, status by batch, and downstream completion. Alert on actionable failure and missed service objectives.
