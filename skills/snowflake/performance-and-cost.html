Snowflake roadmap / 03

Performance and cost

Use query evidence to find bottlenecks, choose the right scaling action, and manage credits while preserving workload SLAs.

InvestigateTuning examplesPractice

01 / Investigation

Start with Query Profile and history.

Queue time

Separate time waiting for warehouse capacity from time spent executing. Queueing points toward concurrency or workload isolation.

Scan and pruning

Compare partitions scanned to total partitions and inspect bytes read. Check whether predicates are selective and compatible with the stored types.

Joins and spill

Look for join row growth, skew, expensive sorts, and local or remote spilling. Confirm whether the join keys and source grain are correct.

Measure the change

Benchmark on representative data. Compare elapsed time, queue time, partitions scanned, and credits before and after a single targeted change.

02 / Tuning decisions

Fix the bottleneck you can show.

Reduce unnecessary scans

Select only needed columns and filter with predicates that allow pruning. Avoid repeatedly processing unchanged data when incremental logic is appropriate.

Resize for compute

Benchmark warehouse sizes when a query is compute-bound or spilling. A larger warehouse may help, but it increases credits per unit time.

Scale for concurrency

Use multi-cluster scaling or workload separation when query queues show concurrent demand, not as a blanket fix for slow SQL.

Control idle spend

Configure auto-suspend and auto-resume to match usage patterns. Monitor warehouse metering and set resource monitors or alerts where appropriate.

SELECT query_id, warehouse_name, total_elapsed_time,
       bytes_scanned, partitions_scanned, partitions_total
FROM snowflake.account_usage.query_history
WHERE start_time >= DATEADD(day, -1, CURRENT_TIMESTAMP())
ORDER BY start_time DESC;
Note: Account Usage views can have latency and require suitable privileges. Use the appropriate Information Schema function for faster, scoped operational checks.

03 / Practice

Interview checks.

A query is slow, but the warehouse is not queued. What would you inspect?

Use Query Profile to inspect scanning, pruning, join behavior, spilling, and operator time. Compare with a known-good run and check data volume and distribution before resizing the warehouse.

When would clustering be worth its cost?

Consider it for large tables where frequent selective filters or joins are not pruning effectively and workload measurements show recurring benefit. Account for reclustering credits and storage effects, and test before adopting it.

How would you reduce credits without harming freshness?

Find idle and oversized compute with metering data, tune expensive scans, and use incremental processing where possible. Validate every change against data freshness, concurrency, and latency objectives.
