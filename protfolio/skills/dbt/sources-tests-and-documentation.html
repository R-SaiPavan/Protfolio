dbt roadmap / 02

Sources, tests, and documentation

Define source contracts, catch data issues with tests, and make models discoverable through documentation.

SourcesYAML examplePractice

01 / Quality checks

Test assumptions close to the model.

Source freshness

Declare freshness expectations where upstream update timestamps support them. Use freshness results to identify stale inputs.

Generic tests

Reusable tests include unique, not_null, accepted_values, and relationships. Apply them to columns whose contract needs validation.

Singular tests

Write a SQL query that returns rows violating a specific business rule. A passing test returns no failing rows.

Documentation

Add descriptions to models and important columns, then generate docs so consumers can explore lineage and definitions.

02 / YAML example

Declare a simple model contract.

version: 2

models:
  - name: stg_orders
    description: Standardized order records
    columns:
      - name: order_id
        tests:
          - unique
          - not_null
      - name: status
        tests:
          - accepted_values:
              arguments:
                values: ['placed', 'shipped', 'returned']
Tip: choose tests based on the business contract. A test that is too broad or encodes an unverified assumption can create noisy failures.

03 / Practice

Interview checks.

What is the difference between a generic and singular test?

A generic test is reusable and parameterized, such as unique or not_null. A singular test is custom SQL for a specific rule and returns the failing rows.

How would you test a relationship between two models?

Use a relationship test on the child key that references the parent model's key, after confirming the intended grain and null policy.

How do you handle a failing test in production?

Assess affected data and consumers, identify whether the failure is a source issue or changed contract, communicate impact, and correct or quarantine data through the approved recovery path.
