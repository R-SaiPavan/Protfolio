Project structure and models

Organize SQL transformations into a dependency graph, use refs for model relationships, and keep project configuration clear.

ModelsExamplePractice

01 / Concepts

Build a directed transformation graph.

Models

A model is a SQL select statement saved in the project. dbt materializes it according to configuration and target.

ref()

Use ref() to reference another model. It creates a dependency edge and resolves the correct relation for the active target.

Sources

Use source() to declare raw inputs, document lineage, and optionally define freshness expectations.

Project organization

Separate staging, intermediate, and mart layers when it clarifies ownership and transformation intent. Keep names and folders consistent.

02 / Example

Reference models, not hard-coded relations.

WITH source_orders AS (
  SELECT *
  FROM {{ source('sales', 'orders') }}
),
customer_totals AS (
  SELECT customer_id, SUM(order_total) AS total_sales
  FROM source_orders
  GROUP BY customer_id
)
SELECT *
FROM customer_totals
Dependency example: if fct_orders uses ref('stg_orders'), dbt records that edge in the DAG and builds the upstream model before the downstream model.

03 / Practice

Interview checks.

What does ref() provide beyond a table name?

It resolves the relation for the active target and records a dependency in the DAG so dbt can order builds and show lineage.

Why separate staging and mart models?

Staging standardizes raw source structures; marts expose business-ready datasets. Clear layers make logic easier to test, understand, and reuse.

How does dbt determine build order?

It parses dependencies such as ref() and source() calls to construct a directed acyclic graph, then schedules upstream nodes before dependents.
