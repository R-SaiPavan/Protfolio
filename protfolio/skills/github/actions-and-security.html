GitHub roadmap / 04

Actions and security

Automate repeatable repository checks while applying least privilege to workflows, tokens, and secrets.

WorkflowsSecurity examplePractice

01 / Workflow model

Automate events with explicit permissions.

Events

Workflows can run for repository events, schedules, or manual dispatch. Choose triggers that match the intended validation or deployment stage.

Jobs and steps

Jobs run on a runner and contain ordered steps. Jobs can have dependencies, separate environments, and distinct permissions.

Artifacts and caches

Artifacts preserve outputs for later jobs or review; caches speed repeat work but should not substitute for trustworthy build outputs.

Secrets and tokens

Use protected secrets and the narrowest required token permissions. Avoid exposing secret values in logs, command output, or artifacts.

02 / Security checklist

Make the workflow's authority explicit.

permissions:
  contents: read

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: echo "Run project checks here"
Example: a validation workflow often needs read access to repository contents, not broad write permissions. Pin and review third-party actions according to the repository's supply-chain policy.

03 / Practice

Interview checks.

How would you design CI for a data transformation repository?

Run fast checks on pull requests, validate SQL or project configuration, and build or test the changed selection where supported. Separate deployment credentials and production jobs from general validation.

How do you protect secrets in GitHub Actions?

Store them in protected repository or environment settings, restrict who can run deployment jobs, use minimal token permissions, and prevent secrets from being printed or uploaded.

Why should third-party actions be reviewed?

Actions execute code in the workflow environment. Review source and permissions, follow the organization's version-pinning policy, and update dependencies through a controlled process.
