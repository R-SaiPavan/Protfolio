PowerCenter roadmap / 04

Performance and recovery

Diagnose where a mapping spends time, tune the measured bottleneck, and design a recovery path for failed or partial runs.

DiagnoseTuning examplesPractice

01 / Diagnosis

Find the slowest part of the pipeline.

Session logs

Check row counts, transformation timings, errors, cache activity, and source or target wait time.

Source and target

Look for slow queries, network waits, target contention, indexes, and commit behavior.

Transformation path

Inspect filters, lookups, aggregations, sorts, and data movement. Confirm the mapping is not doing unnecessary work.

Data skew

Uneven key distribution or partitioning can leave some processing threads with substantially more work than others.

02 / Tuning and recovery

Change one measured bottleneck at a time.

Reduce rows early

Push appropriate filters toward the source when semantics and source capability allow it, then verify the query and row counts.

Partition carefully

Use partitioning only when volume and source/target behavior can benefit. Watch for skew and resource contention.

Capture rejects

Set clear rules for malformed or invalid rows, preserve error context, and alert on unexpected reject rates.

Define restart points

Use batch identifiers and separate staging from publishing so a failed run can resume without duplicate target effects.

Example: if target writes dominate session time, inspect target indexes, constraints, commit settings, and concurrent workloads before changing transformation logic.

03 / Practice

Interview checks.

How do you determine whether the source or target is the bottleneck?

Use session logs and source/target database evidence to compare read, transformation, and write timings. Check waits, row throughput, and commit behavior before selecting a tuning action.

What would you review after enabling partitioning?

Compare throughput and elapsed time, inspect partition balance and skew, and verify resource use and correctness on representative data.

How do you recover after a partial load?

Identify the last successful step and affected batch, reconcile target state, clean or isolate partial output as defined by the runbook, then restart from a safe idempotent point.
