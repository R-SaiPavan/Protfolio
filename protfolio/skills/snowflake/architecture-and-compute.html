Architecture and compute

Understand how Snowflake separates storage, compute, and cloud services, then connect that model to warehouse sizing and workload concurrency.

ArchitectureCompute examplesPractice questions

01 / The platform

Three layers, independent responsibilities.

Cloud services coordinate authentication, metadata, query optimization, and transactions. Virtual warehouses provide compute. Managed storage keeps the data in micro-partitions. Multiple warehouses can work with the same stored data while remaining isolated from one another.

02 / Compute decisions

Choose the scaling action that matches the bottleneck.

Resize a warehouse

Add compute capacity when an individual query or workload benefits from more resources. Benchmark before and after; a larger warehouse can cost more credits and will not fix inefficient SQL by itself.

Scale out for concurrency

Use multi-cluster warehouse scaling when concurrent workloads queue for resources. Additional clusters help serve more concurrent work; they do not guarantee that a single query runs faster.

Control idle spend

Use auto-suspend to stop idle compute and auto-resume when work arrives. Choose a suspend interval that balances startup latency with idle credit consumption.

Isolate workload types

Separate transformation, reporting, and ad hoc workloads when resource contention or ownership makes isolation valuable. Measure the operational and cost impact of extra warehouses.

Interview framing: explain the observed bottleneck first, then justify resizing, adding clusters, or separating workloads with query history and queueing evidence.

03 / Practice questions

Check your understanding.

How can two warehouses query the same Snowflake data without sharing compute?

Warehouse compute is independent of the managed storage layer. Each warehouse runs its own queries and can access the same stored objects, enabling workload isolation without duplicating the data.

A dashboard has queued queries, but each query runs quickly once started. What would you investigate?

Investigate concurrency and warehouse queueing first. Review workload overlap and warehouse load, then consider workload isolation or a multi-cluster warehouse. Resizing may not address the main issue if the bottleneck is concurrent demand.

A single transformation query is slow with little queueing. What would you compare before changing warehouse size?

Compare Query Profile, partitions scanned, bytes read, join behavior, and spilling. Check whether pruning is effective and whether the query or input volume changed. Benchmark a size change only after identifying a compute-bound workload.
