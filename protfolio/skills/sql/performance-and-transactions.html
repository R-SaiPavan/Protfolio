SQL roadmap / 04

Performance and transactions

Read query plans, reduce unnecessary work, and use transactions to protect data changes.

PerformanceTransactionsPractice

01 / Performance

Measure before rewriting.

Execution plan

Inspect access paths, estimated rows, join methods, sorts, and expensive operators. Compare estimates to actual behavior when the database exposes it.

Predicates

Filter early when semantics allow. Keep predicates compatible with indexed or partitioned columns and avoid unnecessary casts or functions around filter columns.

Projection and joins

Read needed columns only. Check join cardinality, key uniqueness, and whether aggregates should be computed before joining.

Indexes and statistics

Indexes and statistics are engine-specific. Use the target database's plan and telemetry, and evaluate maintenance and write costs as well as read speed.

02 / Transactions

Keep related changes consistent.

Atomicity

Group logically related changes so they commit together or roll back together, according to the engine and transaction boundaries.

Isolation

Understand the configured isolation behavior and how concurrent reads and writes can affect the transaction.

Batch commits

Choose commit frequency based on recovery, locking, log or spool pressure, and workload limits; test with representative volume.

Safe retry

Use stable batch identifiers and idempotent writes so a retry after an uncertain failure does not duplicate results.

BEGIN TRANSACTION;

UPDATE account_summary
SET balance = balance - 100
WHERE account_id = 101;

UPDATE account_summary
SET balance = balance + 100
WHERE account_id = 202;

COMMIT;
Note: transaction syntax and autocommit behavior vary by database and client. Confirm the execution environment before using a pattern.

03 / Practice

Interview checks.

How would you investigate a slow SQL statement?

Inspect its plan and runtime metrics, then check scans, filters, join cardinality, sorts, statistics, and concurrency. Make one measured change and compare results.

Why avoid applying a function to a filtered column?

It can prevent some engines from using an index or pruning efficiently. Prefer a range or equivalent predicate that preserves the column expression when possible, then confirm in the plan.

How do transactions help an ETL load?

They can keep a group of target changes consistent. Pair them with batch tracking and a restart strategy so partial failures can be safely retried.
